How AvaVideoPlayer works

One Avalonia application. One shared player UI, control theme and playback logic. Desktop and WebAssembly hosts register different media backends.

One shared application and theme

Both entry points launch the same App and ScreeningRoom from AvaVideoPlayer.Sample. The Grid, Button, Slider, ComboBox, thumbnail Image controls and all playback event handlers live in that shared project. ScreeningRoomTheme.axaml contains their Avalonia templates. The HTML demo is a visual reference and separate backend test harness.

VideoPlayer is the Avalonia UI control. It calls IVideoBackend for opening, transport, seeking, audio, tracks and camera state. VideoPlayerPlatform.CreateBackend selects the platform implementation before controls are constructed.

Desktop pipeline

FFmpegVideoBackend connects the control to PlaybackEngine. The engine manages playback state, bounded queues and synchronization. The FFmpeg adapter crosses the avavideo C ABI through .NET interop. FFmpeg performs demuxing/decoding; libswscale converts video, libswresample handles PCM conversion, libavfilter provides audio processing, and libass renders styled subtitles.

Decoded video is presented through Avalonia or the optional Skia presenter. Decoded PCM is sent through the platform audio adapter. The native package stores runtime assets under their RIDs; NuGet selects them for the consuming application.

Why DevTools shows HTML

Avalonia renders the application controls into its avalonia-canvas. The avalonia-native-host div shown in DevTools contains only the player’s bounded media surface: a browser video element and a WebGL canvas for 360°. Seeing that div does not mean the buttons or catalog are HTML controls. The second canvas has a different job from the Avalonia UI canvas.

Browser media pipeline

The application UI and VideoPlayer control run in .NET WebAssembly with Avalonia. BrowserVideoBackend embeds a browser media surface through NativeControlHost / JSObjectControlHandle, and connects through .NET JavaScript interop to the included avavideo.js module. HTMLMediaElement handles browser codec decoding, seeking and sound output. Flat video uses the media element; 360° video uses that video as a WebGL texture with a perspective camera. Local files become Blob URLs. Web Audio is used by the demo’s optional decoded-sound checks.

Hardware preferences

The native decoder can ask FFmpeg to create a hardware device using av_hwdevice_ctx_create. The available device types and codecs depend on the built profile and machine. Hardware preference, fallback and require-hardware modes are distinct; this diagram does not imply device certification.

Inside the single NuGet

Logical separation is preserved in the assemblies and namespaces. Consumers install one AvaVideoPlayer package. See package contents and execution coverage.
